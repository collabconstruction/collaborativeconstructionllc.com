### Section 1a — Legacy redirect status code: 307 → 301 (deployed to production 2026-10-12 night; see `docs/releases/2026-10-12-seo-redirect-release.md`)

**Root cause of the 307 (confirmed against Cloudflare's own documentation, not assumed):** these 17 paths are served directly by Cloudflare Workers Static Assets' built-in `html_handling` auto-trailing-slash/`.html`-stripping behavior, because `wrangler.jsonc`'s `run_worker_first` only routed `/api/*` through the custom Worker — every other path, including these legacy forms, went straight to the Assets binding, bypassing `worker/index.js` entirely. Cloudflare's documentation (`workers/static-assets/routing/advanced/html-handling/`) states this redirect is **fixed at 307 for every `html_handling` mode and is not configurable** via `wrangler.jsonc` or any other setting.

A second, previously latent bug was found while fixing this: `worker/index.js`'s existing `.html`-stripping branch (`cleanPath = url.pathname.slice(0, -5)`) would have produced an **intermediate, non-canonical redirect target** if it ever ran — e.g. `/about.html` → `/about` (no trailing slash), not `/about/` — which would have been a two-hop redirect chain, not the single permanent hop the owner asked for. This branch was never reachable in production (same `run_worker_first` scoping reason), so the bug had no live effect, but it would have resurfaced the moment the routing was widened.

**Fix implemented and deployed to production (2026-10-12 night, Worker version `af880324-009c-48b2-80b0-eba3bf891f72`):**
- `wrangler.jsonc` — `run_worker_first` widened from `["/api/*"]` to `["/api/*", ...]` plus the 17 exact legacy paths, listed literally (no wildcard). No other path is affected; every canonical page, every asset, and every other route continues straight to Assets exactly as before.
- `worker/index.js` — replaced the old regex/string-stripping `.html` branch with a static 17-entry `Map` (`LEGACY_REDIRECTS`) where every value is already a final canonical URL, so a redirect can never chain into a second redirect. Each match returns `Response.redirect(..., 301)`, preserving the query string.
- **Verification:** `npm test` (84 tests, 82 pass, 2 pre-existing skips under Node 20 / 84 pass 0 skips under Node 22, 0 fail — including a new test asserting all 17 exact redirects, a test confirming no destination is itself a source key in the table, and a test confirming `/api/contact` and an arbitrary unmatched path are unaffected), `npm run build`, `node scripts/verify-release-build.mjs`, and `wrangler deploy --dry-run` all pass. **Deployed to production 2026-10-12 night** from an isolated clean worktree at the exact approved commit `d0bd6607a57c96cc91554f4a86212ea79d7863ac`; live production re-verification confirmed all 17 redirects now return 301 in exactly one hop, all 9 canonical pages still 200, sitemap/robots/assets/`/api/contact` unaffected. Full evidence in `docs/releases/2026-10-12-seo-redirect-release.md`.
- This directly answers the `/about` stale-duplicate-index finding (Section 3's original finding, re-confirmed in Section 3a): the 307 was never going to give Google a strong consolidation signal; once this fix is deployed, `/about.html`/`/about` will 301 straight to `/about/` in one hop.

### Section 4a — Careful reconciliation: owner's "Couldn't fetch" UI observation vs. the API's `isPending: true` (2026-10-12, later still the same day)

The owner reported seeing **"Couldn't fetch"** in the Search Console *UI*'s Sitemaps report after submitting `sitemap.xml` there. This read-only audit's tool only calls the Sitemaps *API* (`sitemaps.list`), which returns `isPending: true` — a different field, not the UI's literal message. These must not be treated as interchangeable without checking what each one actually means, so, per instruction, here is the careful reconciliation rather than an assumption:

- **The sitemap is confirmed submitted — not a candidate for "never submitted."** `sitemaps.list` only enumerates sitemaps Google already knows about (submitted via the Search Console UI/API, or auto-discovered via `robots.txt`); a sitemap with no submission record of any kind would not appear in this list at all. It does appear — one entry, `https://collaborativeconstructionllc.com/sitemap.xml` — so some registration of this sitemap with Google unambiguously exists. This audit does **not** claim the sitemap was never submitted, and the evidence does not support that claim.
- **What `isPending: true` actually means, per Google's own API reference** (`developers.google.com/webmaster-tools/v1/sitemaps`, fetched live this update): *"If true, the sitemap has not been processed."* That is the literal, documented field meaning — not "never submitted," not "actively being reprocessed after a resubmission," just "not yet processed."
- **Why the UI's "Couldn't fetch" and the API's "not processed, 0 errors" are not necessarily in conflict:** `errors: 0` and `warnings: 0` alongside `isPending: true` means this specific API snapshot carries no recorded fetch/parse failure for the sitemap — but the UI message could reflect (a) an earlier point in time, before this session's monitoring began, whose transient error state is not retained in the current `sitemaps.list` snapshot; (b) a UI-specific check (e.g. a live "fetch now" probe at the moment the owner viewed the page) that is not the same operation as the API's processing-status field; or (c) the same underlying "not yet processed" condition, described by two different Google-authored surfaces using different, not-perfectly-synonymous language. **This audit cannot determine with certainty which of these explains the owner's original observation**, because the Sitemaps API does not expose a historical log of individual fetch attempts or their HTTP-level results — only the current aggregate state. That is a genuine limitation of the available read-only tooling, not an assumption being made to fill the gap.
- **What can be stated with confidence:** the sitemap file itself is valid XML, lists exactly the 9 canonical URLs with valid `<lastmod>` values (re-confirmed, Section 4), and is reachable at `/sitemap.xml` with `200 OK` and the correct `application/xml` content type (re-confirmed via the local integration test, Section 1b, and previously via live production curl). There is no evidence of a structural defect in the sitemap file. Separately, **8 of the 9 canonical pages are indexed anyway** (Section 3a, re-confirmed again this update — identical result, no drift since the prior recheck), which happened via Google's own discovery/crawl process, independent of whatever the sitemap's own processing status is. The sitemap's `isPending` status is not currently blocking indexing of the pages that matter.
- **No resubmission was made in reaching this conclusion** — only `sitemaps.list` (read) was called, consistent with the explicit instruction not to resubmit without separate approval.

### Section 6a — `www` 522 root cause (determined 2026-10-12, later the same day)

Investigated via the Cloudflare API using the existing wrangler OAuth credential (zone `5a7f4b95bbd85c1ec0931a6fdd3e1e6d`), scoped strictly read-only:

- **Worker custom domains** (`GET /accounts/{id}/workers/domains?zone_id=...`): only `collaborativeconstructionllc.com` (apex) is bound to the `collaborativeconstructionllc-com` Worker. **No custom domain binds `www`.** (An unrelated second binding, `tinkerloop.collaborativeconstructionllc.com` → a different Worker service, also exists in this zone — not relevant to this investigation.)
- **Zone-level Worker routes** (`GET /zones/{id}/workers/routes`): empty. Confirms `wrangler.jsonc`'s lack of a `routes` key reflects reality, not a local omission.
- **Live re-check:** `www` still resolves via DNS to the same Cloudflare anycast IPs as the apex (i.e., it is proxied/orange-cloud), and both `https://www.../ ` and `https://www.../about/` still return 522 in ~0.13 seconds — fast enough to indicate Cloudflare fails to connect to *any* backend immediately, rather than timing out waiting on a slow real one.
- **Root cause:** a proxied DNS record exists for `www`, but nothing (no Worker custom domain, no Worker route, no other origin) is configured to actually serve requests for that hostname. Cloudflare proxies the connection, then has no backend to reach, and returns 522.
- **Access gap, documented not worked around, rechecked 2026-10-12 (later the same day, again):** re-ran the same read-only probes under this update — `GET /zones/{id}/dns_records?name=www...`, `GET /zones/{id}/rulesets/phases/http_request_dynamic_redirect/entrypoint` — both still return `401`/`10000 Authentication error`. The token's granted scopes (confirmed via `wrangler whoami`: `zone:read`, `workers:write`, `d1:write`, `ssl_certs:write`, etc.) do not include a DNS-records-read or rulesets-read grant; `zone:read` alone is insufficient for either endpoint in Cloudflare's current permission model. Zone metadata itself (`GET /zones/{id}`) succeeds with this token, confirming the gap is scope-specific, not a dead credential. The exact DNS record (e.g. a CNAME to the apex vs. a placeholder A record) still could not be read; closing this needs either the owner checking the dashboard directly or granting a token scoped for `DNS Settings:Read` / `Zone Rulesets:Read`.
- **Recommended fix — syntax corrected 2026-10-12 (later the same day), re-validated against Cloudflare's current documentation, not applied — needs owner approval in the Cloudflare dashboard:** the original draft of this fix (written earlier the same day) proposed target syntax `https://collaborativeconstructionllc.com${uri.path}${uri.query}`, which **is not Cloudflare's documented Redirect Rule syntax** — Cloudflare has no `uri.path`/`uri.query` template variables in this product. The owner caught this before any rule was created. The corrected, owner-supplied and now doc-verified configuration is a **Single Redirect** (Rules → Redirect Rules → Create rule → "Single Redirect"):

  | Field | Value |
  |---|---|
  | When incoming requests match → Custom filter expression / wildcard | Request URL: `http*://www.collaborativeconstructionllc.com/*` |
  | Then → Type | Dynamic |
  | Then → Target URL (expression) | `https://collaborativeconstructionllc.com/${2}` |
  | Preserve query string | Enabled |
  | Status code | 301 (Permanent), or 308 (Permanent, method preserved) — see note below |

  **Why this syntax is correct, per Cloudflare's own docs (`developers.cloudflare.com/rules/url-forwarding/...`, fetched 2026-10-12):** each literal `*` in the "Request URL" wildcard pattern becomes a numbered capture group, referenced in the target as `${1}`, `${2}`, … in left-to-right order of appearance — Cloudflare's own example target is `https://${1}.example.com/t${2}st` for a pattern with two wildcards. The pattern used here, `http*://www.collaborativeconstructionllc.com/*`, has exactly two wildcards: the scheme wildcard (`http*`, matching `http` or `https`, captured as `${1}` but intentionally unused in the target since the target hardcodes `https`) and the path+query wildcard (trailing `/*`, captured as `${2}`). This matches Cloudflare's own worked example's numbering rule exactly, and differs from Cloudflare's own documented *generic* "Redirect from WWW to root" cookbook example (`https://www.*` → `https://${1}`, HTTPS-only, one wildcard) only in that it (a) also catches plain-HTTP requests to `www` in the same rule instead of relying on a separate HTTP→HTTPS step, and (b) pins the match to the exact literal hostname `www.collaborativeconstructionllc.com` rather than the generic `www.*` pattern — which is the correct choice here, see the scope-safety check below.
  - **Preserve query string** is confirmed (via Cloudflare's Single Redirects settings doc) to be a **separate toggle from the status code**, defaulting to **disabled** — it must be explicitly turned on, exactly as the owner specified.
  - **301 vs 308:** Cloudflare's docs state that 301/302 redirects "might" cause a client to switch a `POST` request to `GET` when following the redirect, while 307/308 are documented to preserve the original HTTP method. This host serves no POST endpoint today — `/api/contact` is only reachable on the apex, confirmed again in Task #19's integration test — so a plain `301` is sufficient for the common case (browser GET traffic, old bookmarks, backlinks). **308 is the safer choice only if the owner wants to guarantee correct behavior for any possible non-GET request that might someday hit `www` (e.g., a stale external form action or API client still pointed at the old host)**; either is consistent with "permanent redirect" semantics. This is the owner's call per the original instruction ("301, or 308 if preserving HTTP methods matters") — not applied either way pending approval.
  - **Scope-safety, re-confirmed:** the pattern `http*://www.collaborativeconstructionllc.com/*` matches only requests whose host is the exact literal string `www.collaborativeconstructionllc.com`. It does **not** match the apex (`collaborativeconstructionllc.com`, no `www.` prefix — different literal string, not a prefix/suffix match), and does **not** match the unrelated `tinkerloop.collaborativeconstructionllc.com` custom domain confirmed in the bullet above (that hostname does not start with the literal substring `www.`, so the pattern cannot match it even though `*` wildcards can span multiple characters). No other host or service in this zone is affected. This rule requires no code or Worker change and cannot create a redirect loop (the target host, `collaborativeconstructionllc.com`, never matches the rule's own `www.`-only trigger pattern, so a single hop always terminates).
- **Rejected alternative:** adding `www` as a second Worker custom domain bound to the same Worker. That would resolve the 522 but would make `www` serve the *entire site identically* (true duplicate content) rather than redirect, since the Worker's own `www`→non-www redirect branch in `worker/index.js` only executes for paths actually routed through the Worker (`/api/*` plus the 17 legacy paths after Section 1a) — making it cover `www` for all pages would mean widening the Worker's routing scope for every single page request on that host, a materially larger and riskier change to the request path that also handles customer intake. Not recommended.
