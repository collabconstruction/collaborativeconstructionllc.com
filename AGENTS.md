## Frontend context (read this before any UI/design work)

Goal of this section: let an agent doing visual/design work skip re-discovery and start editing immediately.

- **Stack**: Eleventy (`@11ty/eleventy` v3) static site generator, config at `eleventy.config.js`. Source `src/` → output `_site/`. `npm run build` (`rm -rf _site && eleventy`, cleans first — stale deleted assets have shipped to prod before when this step was skipped). `npm run serve` for a bare Eleventy dev server, or use the Claude Preview MCP tools with the `"site"` config already defined in `.claude/launch.json` (`npx @11ty/eleventy --serve --port=8787`) to iterate visually without a manual terminal.
- **One shell template, not four**: `src/_includes/base.njk` is the single page shell (head, header, footer, JSON-LD) for every page. Its own front-matter doc comment at the top of the file lists every variable a page can/must set (`title`, `description`, `permalink`, `canonical`, `schemaType`, etc.) — read that comment before adding a new page.
- **Pages**: `src/index.njk` (home), `about.njk`, `gallery.njk`, `construction-advisory.njk` (renders one `Service` JSON-LD node per entry in `src/_data/services.json` on a shared page), and five dedicated service-landing pages (`adu-builder-cape-cod/`, `custom-home-builder-cape-cod/`, `home-additions-cape-cod/`, `home-renovation-cape-cod/`, `general-contractor-falmouth-ma/`) each emitting its own single `Service` node. Shared content (nav items, business info, service list, team) lives in `src/_data/*.json` — prefer editing data files over hand-editing repeated markup.
- **Color system is almost entirely CSS custom properties.** `css/styles.css` defines the full palette in one `:root` block (`--maroon*`, `--amber*`, `--gold-1/2/3`, `--ink`, `--body`, `--muted`, `--cream*`, `--stone`, `--white`, `--line`, plus shadow tokens). Nearly every component rule references these variables rather than literal colors, so **a full re-theme is primarily a `:root` edit**, not a file-by-file rewrite. As of the October 2026 redesign the palette is a flat "Contractor Industrial" charcoal (`#2b2d31`) + orange (`#d9531e`) scheme (previously maroon/gold); variable *names* were deliberately kept stable through that change so this remains true for the next redesign too.
  - After changing `:root`, grep `css/`, `js/`, and `src/` for literal `rgba(`/hex colors — there are still ~15-20 hardcoded rgba-literal blocks (glow/shadow accents, SVG inline styles are rare) and a few JS color-string arrays (see below) that don't derive from the variables and need matching by hand.
  - `js/main.js` also contains hardcoded color literals: the click-burst `COLORS` array, an ambient-dust `tints` array (used twice), and the `SPOT_TARGETS` array (ambient glow-orb colors/positions behind the about/advisory sections). Grep `main.js` for raw `rgba(`/hex strings when re-theming.
- **Decorative vs. functional JS/CSS — know which is which before deleting something:**
  - *Purely decorative, safe to restyle or remove for a different aesthetic*: click-burst particles (`.spark-layer`/`.spark`/`.dust`, `makeDot`/`makeDust` in `main.js`), ambient glow orbs (`SPOT_TARGETS`, `.amb-spot`), the spinning conic-gradient border on the carousel/owner photo (`frameSpin`). A former trailing custom cursor (`.cc-cursor`) was **removed in October 2026** — the site now uses the plain OS/browser default cursor everywhere; don't reintroduce a custom cursor unless explicitly asked.
  - *Functional, preserve behavior even when restyling*: scroll-reveal (`[data-reveal]`, `[data-reveal-words]`), the directional page-transition system (`.page-main`, `html.enter-right`/`enter-left`, `pageIn*` keyframes, the inline pre-paint script in `base.njk`'s `<head>`), mobile nav toggle, sticky header scroll-shadow, back-to-top button, the cookie-consent banner (gates GA4 — see `analytics.js`), and the intake form (`form_start` tracking in `intake-context.js`, Turnstile challenge lifecycle). All decorative JS is gated behind `prefers-reduced-motion` (`prefersReduced` in `main.js`) — keep that gate on anything new.
  - Previously removed (don't resurrect without being asked): the animated gold-sparkle ambient background (`body::before`, `.bg-fx__*` layers) and the "bubble panel" section styling (large border-radius + tinted background + glow shadow on `.section > .container` etc.) — both were part of the pre-October-2026 look and are now flat/transparent by design.
- **Verify before calling UI work done**: `npm test` (`node --experimental-vm-modules --test tests/*.test.mjs`; some pre-existing failures are unrelated to styling — see `docs/HANDOFF.md`/local Node-version notes before assuming a regression), `npm run build`, `node scripts/verify-release-build.mjs`. For a real deploy: `npm run release:check` (tests + build + verify + `wrangler deploy --dry-run`), then follow the isolated-worktree release discipline documented in `docs/releases/`.

## Backend context

- **Runtime**: Cloudflare Worker (`worker/index.js`) + D1 database, deployed as `collaborativeconstructionllc-com`. `wrangler.jsonc` is the real config; `wrangler.local.jsonc` is for local-only work (no email binding, never sends notifications) and is what `npm run dev`/`npm run db:local` use.
- **Lead/intake data is private and off-limits to casual reading.** Real customer records must never be printed to a terminal an agent can see, pasted into chat, or committed. Operational access goes through `scripts/leads.mjs` (`queue`/`export`/`add`/`update`/`history`/`report`, each requiring an explicit `--local`/`--remote` flag and an absolute, outside-the-repo, permission-600 output path) and the local-only `scripts/dashboard.mjs` viewer. Full rules — retention, redaction, what's safe to share with an agent (assigned record or sanitized aggregates only, never a full export) — are in `docs/operations.md`; read it before touching anything lead-related.
- **Credentials rule (hard constraint, not a style preference)**: never type, paste, or otherwise enter a real API key, token, password, or credential into any file, command, or field yourself, regardless of who authorizes it. The user enters those directly (`wrangler secret put` interactively, or a dashboard UI). This applies to Cloudflare, D1, GSC, GA4, email, and anything else.
- **Migrations**: production already has both `0001_existing_leads.sql` and `0002_lead_operations.sql` applied; its migration ledger only records the first. **Do not replay or re-apply either migration against production** — that reconciliation is separate, deliberately deferred maintenance. `npm run db:local` is safe (fresh synthetic local D1 only).
- **Tests**: `node --test tests/lead-operations.test.mjs` exercises real SQLite migrations, workflow/stage-sync logic, notification-state handling, and report date-boundary logic against Python's stdlib SQLite + Node's built-in test runner — no live account access needed.
- For current deployment/Git branch state and what's committed vs. not, read `docs/HANDOFF.md` section 1 first — it's the single source of truth for "what's actually live right now," and it goes stale fast, so trust it over memory of past sessions.
